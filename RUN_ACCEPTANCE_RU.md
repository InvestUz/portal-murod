# Полная техническая проверка комплекта 0.3.0-rc.12

Одна команда создаёт отдельный одноразовый стенд с вымышленными данными. GitHub и пакеты Python приложения на хосте не нужны. По решению владельца эту общую команду выполняет ИТ на Linux-стенде. На Windows она честно остановилась на host guard (exit 2), хотя Docker Desktop доступен. Отдельно выполнены настоящие сборки, PostgreSQL, HTTPS, AV/OCR, шифрованное восстановление и security scans: см. docs/RC12_TECHNICAL_STATUS_RU.md. Это не полный прогон штатного Linux install.

## Подготовка

Нужна отдельная Linux x86_64 VM/сервер: Python 3.10+, OpenSSL, стандартный локальный Docker Engine и Compose 2.24+, минимум 4 vCPU, 12 ГиБ RAM и 40 ГиБ свободного диска. Рекомендуется 16 ГиБ RAM. Оператор должен иметь доступ к Docker; контекст — локальный `/var/run/docker.sock`.

Нужен доступ к официальным реестрам образов, Alpine APK, Python/npm, nodejs.org, OCR-моделям, базам Trivy и свежим сигнатурам ClamAV. На стенде не должно быть настоящих данных сотрудников. Ошибки антивируса и находки High/Critical нельзя устранять отключением проверки.

## Запуск

Распакуйте папку `portal` из архива исходников. Из неё выполните:

```bash
python3 operations/acceptance.py --work-dir /var/tmp/toshkent-acceptance-01
```

Если доступ к Docker требует `sudo`, запустите эту команду с `sudo`. Каталог должен быть новым и находиться вне исходников. Для повторного прогона используйте другое имя каталога. Изменённые исходники, не соответствующие включённому `RELEASE-MANIFEST.json`, отклоняются. Git для выполнения команды не нужен.

## Что выполняется

1. Проверка целостности комплекта, совместимости локального Docker и принадлежности ресурсов до первой сборки. Создание двух отдельных Compose project, секретов, имён образов, томов и локального тестового TLS-сертификата.
2. Сборка Python API/worker и отдельного проверочного образа. Настоящий PostgreSQL, весь pytest без допустимых пропусков, отдельная БД для замера поиска и EXPLAIN. Проверочные БД не используются приложением.
3. Штатный `portalctl install`: миграции, ограниченная роль приложения, worker/seccomp/OCR, свежий ClamAV, чистый PDF и EICAR, публикация/поиск/права, первая зашифрованная копия и HTTPS-проверки.
4. HTTPS API-сценарии администратора, HR и сотрудника через настоящий прокси: вход и серверные сессии по выбранной политике, роли/приватность, импорт 150 записей, совпадение ФИО, фото, PDF/Word и поиск, две редакции/старые ссылки, новости/уникальные просмотры, корзина и отзыв сеанса. Решения антивируса и статусы файлов не подменяются.
5. Остановка записи, зашифрованный согласованный снимок, восстановление в другой Compose project с отдельными БД/файловыми томами. Сверка количеств и хешей бизнес-записей, включая аккаунты/MFA, исходных байтов редакций, отказ старому сеансу и новый вход прежним паролем и проверка MFA, если политика требует его. Повторная файловая проверка. Это второй экземпляр на том же хосте, не второй физический сервер.
6. Скан конечных API/worker и всех закреплённых баз. Любой High/Critical блокирует успешный итог, включая находки без исправления. Ошибка стадии не превращает остальные стадии в пройденные.
7. По умолчанию — удаление только своих контейнеров/томов после проверки принадлежности. Отчёты и закрытая диагностика сохраняются; чужие ресурсы не удаляются.

## Отчёт и ручная проверка

Результат: `/var/tmp/toshkent-acceptance-01/evidence/report.json`. Коды выхода: `0` — все автоматические технические стадии пройдены, `1` — есть провал, `2` — несовместимая среда/ошибка начала. В отчёте отдельно указаны выполненные, проваленные и не запущенные стадии. Локальные strict-сканы rc.11 прошли без High/Critical; при установке скан повторяется с актуальной базой и блокирует любые новые находки.

Для передачи результатов используйте только папку `evidence`. Папки `private`, `.deploy`, ключи, пароли, MFA-секреты и полные диагностические логи предназначены только оператору. Не прикладывайте их к сообщениям или публичным отчётам.

Для последующей проверки интерфейса добавьте `--keep-lab` к команде первого запуска. Стенд останется доступен только на `https://localhost:18443` / `https://localhost:18444`. После успешного HTTPS-сценария тестовые аккаунты/MFA находятся в закрытом `private/acceptance-accounts.json`. После восстановления исходный экземпляр остановлен; дальнейшая проверка идёт на восстановленном экземпляре. Тестовый TLS-сертификат не является сертификатом компании. Не открывайте порты во внешнюю сеть.

`productionApproved` всегда остаётся `false`: автоматический прогон не удостоверяет независимый пентест/ретест, браузерную приёмку, DNS/TLS/VPN компании, восстановление на другом физическом сервере, нагрузку/отказы на оборудовании компании или качество OCR реального корпуса. Эти условия перечислены в `externalGates`.

Постоянная установка после технической и внешней приёмки — по [HANDOVER_RU.md](HANDOVER_RU.md), с действительными DNS, TLS и офисными/VPN-сетями. Тестовый стенд не становится постоянным порталом автоматически.
