# Архитектура и права

Браузер получает статические React-файлы и обращается к Django REST API того же origin. Django принимает решения о доступе, валидирует ввод и изменяет данные транзакционно через ORM. В production PostgreSQL хранит бизнес-данные, учётные записи, сессии, аудит и очередь заданий. В стандартном одноузловом профиле закрытый файловый том хранит непубличные файлы; S3 остаётся дополнительным вариантом. Отдельный Python worker получает один файл по короткой аренде через внутренний API; он не получает пароль базы или ключ S3. Нет Redis-зависимости при текущем объёме, нет JavaScript-бэкенда.

| Действие | Сотрудник | HR | Администратор |
|---|---|---|---|
| Читать опубликованные материалы и открытые поля сотрудников | Да | Да | Да |
| Изменить собственные мобильный/видимость/этаж/кабинет | Да | Да | Да |
| Создать и изменить сотрудников, структуру и офисы | Нет | Да | Да |
| Видеть год рождения/скрытые контакты, экспортировать справочник | Нет | Да | Да |
| Публиковать новости/документы, управлять редакциями/корзиной | Нет | Да | Да |
| Учётные записи, роли, сброс пароля/MFA | Нет | Нет | Да |

Карточка сотрудника и учётная запись — разные сущности; связь необязательная и уникальная. Архивирование карточки блокирует доступ и повышает версию сессии; восстановление карточки не включает аккаунт автоматически. Смена роли также отзывает действующие сессии. Внутренний номер не имеет переключателя скрытия. Видимость мобильного и дня/месяца рождения учитывается и в проекции ответа, и в предикатах поиска.

Основные сущности: Office → OrgUnit/Employee; Employee → manager/office/unit/photo; UserAccount → Django User/optional Employee; News → NewsRevision/NewsView; Document → immutable DocumentVersion → FileObject; FileObject → ProcessingJob; ImportJob → preview/decisions/report; AuditLog → actor/action/entity/changed_fields без старых значений персональных полей.

Номера сотрудников выдаёт отдельная последовательность. Предупреждение об одинаковом ФИО допускает явное создание тёзки. Циклы подчинённости/оргструктуры проверяются под блокировкой записи. Для PostgreSQL используется advisory lock, для SQLite — локальная транзакционная блокировка; длительная нагрузка PostgreSQL ещё не испытана.

Файл проходит состояния QUARANTINED → SCANNING → APPROVED либо SCAN_ERROR/REJECTED. Публикация/скачивание требуют APPROVED. Ошибка/устаревшие сигнатуры ClamAV закрывают допуск. OCR выполняется только после допуска. Ошибка OCR не подменяет успехом проверку файла и не уничтожает оригинал. Worker ограничивает время/память/страницы/размер; код парсера запускается отдельным процессом. Это ещё не доказанная защита от всех уязвимостей парсеров: нужны проверка контейнера и независимый пентест.

Редакция документа не обновляется через API. Дополнительный триггер БД запрещает менять её идентификатор, файл, номер редакции, даты и автора; результаты повторного OCR разрешено обновлять. Текущая редакция задаётся отдельно. Старый URL остаётся читаемым с переходом к актуальному. Поиск по содержимому сейчас использует нормализованное совпадение подстроки через параметризованный ORM; Для PostgreSQL добавлены GIN pg_trgm индексы нормализованных названий и содержимого; их применение и план запроса ещё требуют нативной проверки. FTS не используется. Производительность на больших архивах не подтверждена.

Новости имеют черновик/публикацию, закрепление, необязательные даты, санитарную обработку HTML, переводы по желанию. Просмотр фиксируется отдельным POST при открытии полной статьи и уникален по статье/аккаунту. Не проверяется внимание, длительность чтения или понимание; интерфейс не выдаёт поимённый список читателей.

## Профиль передачи 0.3

Одноузловой установочный профиль изменён по ADR 002: стандартное хранилище — закрытый файловый том, а не обязательный внешний S3. Бэкенд сохраняет S3-адаптер как отдельный расширенный вариант. Управляющие команды и сведения для ИТ описаны в HANDOVER_RU.md; ручной подбор внутренних сервисов/паролей для стандартной установки не нужен.

Heartbeat worker содержит сведения о моделях OCR и проверенном seccomp. Readiness проверяет БД/frontend/AV/private storage/worker/модели/изоляцию; health-файл пишет supervisor атомарно в частный tmpfs. Парсер не имеет сети/сигналов родителю, не получает broker/DB/storage credentials; AV-решение и проверку очищенного изображения выполняет supervisor. Это дополнительная изоляция, не доказательство отсутствия уязвимостей ядра/парсеров.

Поиск по распознанному содержимому использует отдельную нормализованную строку с alias для потерь диакритики. Извлечённый текст/оригинальные байты не переписываются. Простое совпадение подстроки сохранено для текущего объёма; Реализация trigram-индексов не объявляется нативно проверенной; измерения этой итерации относятся к SQLite. Масштабная производительность не подтверждена.

Восстановление rc.4: закрытая временная копия ciphertext в backup-work, полная аутентификация до plaintext, распаковка в private-files staging с последующим переносом/откатом. Общей транзакции PostgreSQL + файловый том нет: при несогласованности вход остаётся закрытым и используется страховочный снимок.
